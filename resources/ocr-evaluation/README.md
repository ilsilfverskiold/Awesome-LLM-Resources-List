# OCR Engine Benchmark — 14 Engines × 93 Documents

A structured evaluation of 14 OCR and document-AI engines across 93 documents
spanning 3 difficulty tiers and 12 document types. Engines are scored on text
coverage (automated), LLM judge quality (Gemini 2.5 Pro vision), and table
extraction fidelity (TEDS + judge) for financial documents.

---

## Key Findings

- **Gemini Flash** and **Claude Sonnet 4.6** lead on text content coverage (GT Cov 0.919 and 0.928) with gemini_flash having the best LLM judge score at 0.891/1.0
- **Mistral OCR** is the strongest value-for-money cloud option at $0.001/page (GT Cov 0.875)
- **Marker** is the best free/local option at $0.00094/page with GT Cov 0.814
- **Docling** consistently underperforms (GT Cov 0.569) due to a word-merging bug on many document types
- Hard-tier performance diverges significantly — chart and table extraction separates strong from weak engines
- For **table structure**, mistral_ocr and claude_sonnet_4_6 have the best balance of TEDS score and judge quality

## Evaluation Methods

### GT Coverage (primary text metric)

The fraction of **unique** ground truth words that appear anywhere in the engine
output. Set-based: `|output_words ∩ gt_words| / |gt_words|`.

- Ignores extra output (precision-neutral) — useful for structured engines like
  llamaparse that add headers/labels not in the minimal GT
- Measures whether content was captured, not how it was formatted
- Low coverage almost always means genuinely missing content
- Does **not** apply to silver GT docs (see caveats)

### Why not WER / CER?

The standard OCR metrics — Word Error Rate and Character Error Rate — grade you
on getting the words in the right order. That's fine for a simple page of
running text where everyone reads top to bottom. It falls apart here because
different engines traverse the same document differently: one reads a two-column
layout left-to-right across both columns, another reads each column separately.
Both got every word right, but WER sees them as errors because the sequence
doesn't match.

On top of that, some engines add structure the ground truth doesn't have —
headers, labels, markdown formatting. WER punishes that as wrong words even
when the actual content is correct.

GT Coverage sidesteps both problems by just asking: is this word anywhere in
the output? Order doesn't matter, extra formatting doesn't matter.

Word F1, precision, and recall are still in `scores/per_doc.csv` if you want
them — just be aware that low precision on a structured engine usually means it
added formatting the GT didn't include, not that it got the content wrong.

### LLM Judge

Gemini 2.5 Pro (`gemini-2.5-pro`) with the source image and OCR output. Scores
0–5 on four dimensions: overall, text accuracy, structure, tables.

- **Primary metric for silver GT doc types** where text comparison is circular
- See `evaluation/prompts.md` for exact prompts and response schemas
- Temperature = 0, structured JSON output enforced
- ⚠ Gemini Flash is both judge family (Gemini 2.5 Pro judges) and a tested engine
  (Gemini 1.5 Flash is tested) — different model versions but same family; potential
  calibration bias

### TEDS — Table Edit Distance Similarity

Structural similarity between an extracted HTML table and the textract_structured
reference HTML. 1.0 = identical structure. Used only in `scores/table_benchmark.json`
for the 5 financial table documents.

Applies only to the 9 **structured engines** that can produce table markup:
textract_structured, gemini_flash, claude_sonnet_4_6, mistral_ocr, llamaparse,
marker, docling, mineru, deepseek_ocr.

## Caveats and Known Issues

### Ground Truth Quality

These specific cases have GT issues that make automated text metrics unreliable:

**Silver GT doc types** (newspaper, legal, report, scanned_001–004):
GT was generated by running Tesseract at dataset creation time, not human-verified.
Text comparison metrics are circular — comparing one OCR engine against another.
Only LLM judge scores are valid for these. They are excluded from GT Coverage calculations.

**IAM handwriting** (`hard/handwritten/iam_000–005`):
The IAM dataset uses an academic tokenisation format that places spaces around all
punctuation: `"it 's raining"`, `"B . B . C ."`, `"I T V"`. This inflates the GT
word count by approximately 35%, making all engines appear to have lower coverage
than they actually do. Use the LLM judge score for handwritten documents.

**invoice_001** (`easy/invoice/invoice_001`):
The ground truth contains values only (amounts, dates, reference numbers) with no
field labels. All engines that correctly extract `"Invoice Number: INV-2024-001"`
get penalised on precision for including `"Invoice"`, `"Number"`, etc. Coverage
and recall are reliable; precision is not.

**scanned_001–004** (`hard/scanned_legacy/`):
The benchmark image is page 1 only, but the GT text file contains the full
multi-page document — 2 pages for scanned_001–003, 6 pages for scanned_004
(confirmed by `pgNbr=` markers and "Page X of 2" text in the GT files).
GT word counts: 417 / 879 / 571 / 945 words vs ~200–500 words from page 1.
A perfect page-1 transcription of scanned_004 can only score ~0.38 coverage
because the GT contains 6 pages of content the engine never saw.
These are excluded from all text metrics in `scores/composite.csv` and the
benchmark report. `scanned_000` and `scanned_005` have single-page GTs and
are included normally.

### Judge Reliability

**Conflict of interest**: Gemini 2.5 Pro is used as the judge while `gemini_flash`
(Gemini 1.5 Flash) is one of the tested engines. These are different model
generations from the same family. There may be a calibration bias toward outputs
that resemble Google's style or formatting. Gemini Flash's judge score (0.867) is
notably higher than other top-tier engines; interpret with this in mind.

**Score variance**: Judge scores have session-to-session variance. The same prompt
and document may produce scores ±0.5 in different runs. Absolute scores matter less
than relative ordering, and differences smaller than ~0.5 may not be significant.

**Score = 0 means "not applicable"**: A tables score of 0 means the document has no
tables, not that the engine failed. Equations = 0 means no equations in the document.

**Sample size**: Silver GT covers 22 docs × 14 engines = 308 judge calls for the
main benchmark, and 45 calls (9 engines × 5 docs) for the table benchmark.

### Metric Interpretation

**GT Coverage ≠ completeness**: Coverage is set-based and ignores word frequency.
An engine that outputs every unique GT word once scores 1.0 even if the document
repeats values many times and the engine only captured them once.

**Low precision ≠ bad OCR**: Structured engines (llamaparse, claude, gemini) output
section headers, labels, and formatting that minimal GTs do not include. This
reduces precision and F1 without indicating a quality problem. Coverage is more
reliable for these engines.

**TEDS measures structure, not values**: A table with perfectly correct row/column
structure but wrong cell values can score 0.95 TEDS. Always check the judge
accuracy score alongside TEDS.

**textract_structured text metrics = textract_text**: In `results/ocr_outputs/`,
the `textract_structured.txt` files contain flat extracted text (one word block
per line), identical in content to `textract_text.txt`. The structured output from
Textract — the HTML table representation — was not used for the main text benchmark
since the benchmark only measured text accuracy at that stage. It is preserved in
`documents/hard/financial_table/*_gt.json` (field: `table_html`) and is the
reference used for TEDS scoring in `scores/table_benchmark.json`. This is why
textract_structured and textract_text show identical GT Coverage and F1 scores
in every table above.

**Single-page evaluation**: All documents are single-page images. Performance on
multi-page documents (with context across pages) may differ.
